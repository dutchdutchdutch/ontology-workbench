Getting started

Your first project, from empty folder to pulled sources

One-Vocabulary reads your team's documents, tickets and code, and turns them into one glossary everyone agrees on. This page covers only the first stretch: make the project, describe its sources, pull them, check the pull. Then hand over to the agent.

0

Before you start

  • Open a terminal in this repository's folder. Every command on this page runs from there. No terminal is fine too: step 1 shows the by-hand way.
  • Open Claude Code in the same folder. Claude Code is the assistant that runs the pipeline. It reads the rules in the folder and does the steps for you.
  • Pick a short project name. Lowercase letters, digits and hyphens only. my-bistro is good. Linden Street Bistro is not.

This page follows the worked example in projects/bistro/: Linden Street Bistro, a made-up restaurant whose floor, kitchen and app all use everyday words in their own way. That folder already holds every step, finished. Here you start the same restaurant again as my-bistro, and at each stop you can open projects/bistro/ to see what the result should look like. For your own product, swap in its name.

1

Create the project

One command makes the project folder. Run it in the terminal, from the repository's folder. It copies a blank template and writes in your project name and today's date.

tools/new-project.sh my-bistro
You should see Created projects/my-bistro, then a line telling you to fill project.yaml.
No terminal? Do the same by hand.
  1. In the projects folder, make a new folder named my-bistro.
  2. Open _templates/project. Copy everything inside it into your new folder: the numbered folders, decisions, README.md and project.yaml.
  3. Open project.yaml. Put my-bistro where it says <name>, and today's date where it says <YYYY-MM-DD>.
The result is the same as the command. Nothing else in the workspace cares which way you did it.

The new folder has one numbered subfolder per step. They are empty. That is normal: a step is done when its file appears there, and nothing else tracks progress.

projects/my-bistro/ README.md cover sheet project.yaml ← you fill this next 00-sources/ step 00 writes here 01-terms/ empty for now 02-delta/ 03-merge/ 04-draft/ 05-glossary/ 06-ontology/ 07-streams/ optional lenses, later 08-publish/ what goes out, and when decisions/ rulings go here, later

If the script refuses, the folder already exists. Pick another name. It never overwrites. That is also why this page does not use bistro: the finished example already has that name.

2

Point it at your sources

Open projects/my-bistro/project.yaml. This is the only file that holds anything about your product. Everything else in the workspace is the method and stays the same for every project.

Under sources: there is one block per kind of source. Fill the ones you have. Delete the ones you do not have.

BlockWhat to put inWhere to find it
driveThe id of the shared Google Drive folder, and a cutoff date. Everything under that folder, changed on or after the date, gets pulled.Open the folder in Drive. The id is the last part of the address bar.
linearThe workspace slug, the team key, and a cutoff date.The slug is in the Linear address: linear.app/<slug>. The team key is the prefix on issue numbers, like BIS-123.
codeThe git repo on GitHub as owner/repo, a cutoff date for pull requests, and the branch naming pattern. Despite the name, this is git, not code: the pipeline reads pull request titles and branch names only, never the source files. Those names are a stand-in for the words engineers use.The repo address. Ask an engineer for the branch pattern, or copy a real branch name.
glossaryLeave path: null if the team has no glossary yet.If one exists, put its file in the project folder and set the relative path.

To see a filled-in file, open projects/bistro/project.yaml: a shared Drive folder of staff documents, a Linear team BIS for the booking app, and a GitHub repo for its code, plus the three people who may rule on meaning.

A tool Claude Code cannot reach

Some tools have no connector, or the team does not allow one. Jira, Confluence and SharePoint are common cases. Keep a block for it anyway, with external: true. The pipeline will not pull it. A person runs a ready-made prompt inside that tool and pastes the result back later. Step 3 shows where that lands.

  jira:
    external: true
    type: issue-tracker      # issue-tracker, document-store, or code-repository
    tool: Jira
    link: https://example.atlassian.net
    cutoff: 2026-03-01

Two more blocks worth filling now

  • people: the names who may decide what a term means when the sources disagree. One product person and one engineer is a good start.
  • seed_terms: optional. Five or six words you already know matter to this product. They steer the search toward the product's own words.
Done when Every angle bracket placeholder like <id> is gone, and every source you do not have is deleted.
3

Pull the sources

This is step 00 of the pipeline. Claude Code does it. You ask, in plain words:

Run step 00 for my-bistro.

Claude Code opens the contract for the step, reads your project.yaml, and copies every item from every source into files. It needs a connection to Linear and to Google Drive, and the GitHub command line tool signed in. If a connection is missing, it does not guess. It writes that source down as not pulled and tells you.

This is the only step that goes online to read. (Step 08, at the very end, goes online to send.) It copies. It does not read for meaning. Every step after this reads the copies, which is why re-running a later step is cheap.

You should see A folder 00-sources/raw/ with one subfolder per source and one file per item, plus 00-sources/manifest.md, the receipt.
projects/my-bistro/00-sources/ manifest.md counts per source, one row per item, what was not pulled raw/ drive/ one file per document, deck or sheet linear-docs/ linear-issues/ title, description, linked PR names code/ PR titles and branch names from git, never source files

The finished example shows what this looks like: projects/bistro/00-sources/ holds three staff documents, seven issues and seven pull requests, with the manifest listing every one. (In the example the sources are made up and every link reads EXAMPLE-not-a-real-link.)

An external source such as Jira has no folder here. The manifest lists it under "Inventoried externally", with the name of the prompt file to run inside that tool. That is homework for a person, not a problem.

✓

Check the manifest

Human checkpoint

Open projects/my-bistro/00-sources/manifest.md. Read the counts at the top and the "Not pulled" section at the bottom. This takes ten minutes and saves a glossary built on a third of the evidence.

  • FineCounts look like the size of the company. A row under "Inventoried externally". Both mean carry on.
  • SuspiciousA count that looks low. Three Drive documents from a team with a year of history is a permissions problem, not a small team. Fix access, then ask Claude Code to run step 00 again.
  • StopAny row under "Not pulled". The row says what is needed: which connection, which id. Fix it and re-run. Do not go on with a source missing.

Re-running step 00 is safe. It replaces the raw folder and rewrites the manifest.

When the manifest is clean, step 00 is done. Nothing to mark or tick: the file existing is the status.

4
Next step

From here, ask the agent

This is how every step after this one starts. You do not need to remember the order or the file names. The workspace knows its own status from which files exist, and Claude Code reads that. The next step is 01: it reads each raw folder and lists the terms it finds, with a quote for each.

  • What is next for my-bistro?Claude Code checks which files exist and tells you the next step and why.
  • tools/status.sh my-bistroThe same answer, in the terminal, without the agent.
  • Run step 01 for my-bistro.Starts the term inventory, one file per source.
  • Which sources were not pulled, and what do you need?Use this when the manifest has a "Not pulled" row.
  • Run step 00 again for my-bistro.After you fixed access or edited project.yaml.
  • Explain step 01 in plain words before you run it.Every step has a contract. Claude Code can read it to you.

Every step ends with a checkpoint like the one above. The agent will not run the next step until you have looked.

To see where the road ends, read projects/bistro/README.md. It walks the finished example in order, from the raw sources to the published glossary, the ontology picture and the copies sent out. Run tools/status.sh bistro to see every step done.

Full detail lives in the workspace: README.md for the whole run, projects/bistro/ for a finished example, and factory/steps/00-sources/CONTEXT.md for this step's contract.
